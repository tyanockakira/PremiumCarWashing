# Локальна база PremiumWash 2.0

[Міграції в `migrations/`](migrations/) визначають схему для нового проєкту. [`schema.sql`](schema.sql) збережено як історичне джерело. Не застосовуйте його до нової бази. Він містить застарілі публічні функції запису та правила доступу.

## Міграція та каталог

Застосуйте міграцію до запущеного локального проєкту `premiumwash-2-local` із кореня репозиторію.

```powershell
supabase migration up --network-id premiumwash-2-local-loopback
```

Файл [`seed.sql`](seed.sql) містить лише каталог. Повторний запуск додає відсутні записи за стабільними ідентифікаторами та зберігає поточні ціни й ознаки активності наявних записів. Автоматичне завантаження каталогу вимкнене в `config.jsonc`. Щоб додати каталог без скидання бази, скористайтеся цією командою PowerShell.

```powershell
$OutputEncoding = [System.Text.UTF8Encoding]::new($false)
Get-Content -Encoding UTF8 -Raw supabase/seed.sql |
    docker exec -i -e PGCLIENTENCODING=UTF8 supabase_db_premiumwash-2-local psql -X -U postgres -d postgres -v ON_ERROR_STOP=1 --single-transaction -f -
```

Для відтворення схеми та каталогу на погодженій одноразовій локальній базі використайте `supabase db reset --sql-paths seed.sql --network-id premiumwash-2-local-loopback`. Команда видаляє локальні дані. Параметр `--sql-paths` вмикає завантаження вказаного файлу для цього скидання.

```powershell
supabase test db --network-id premiumwash-2-local-loopback
```

## Межі доступу

Публічні ролі читають активні записи каталогу. Активний працівник бачить також приховані записи каталогу та власні `id`, `role`, `is_active`. Видача ролей, редагування каталогу та доступ до контактів потребують окремого довіреного процесу.


## Контракт серверної перевірки

Захищений RPC доступний серверній ролі й повертає UUID заявки. Його сигнатура та правила повтору наведені в розділі захисту створення заявок.

| Тип | Обов’язкові поля | Необов’язкові поля |
| --- | --- | --- |
| `booking` | `type`, `phone`, `name`, `selection` | `carClassId`, `car`, `date`, `slotId`, `comment` |
| `consultation` | `type`, `phone` | `name`, `car`, `question` |

Для `booking` поле `selection` містить один варіант.

- `{"kind":"service","slug":"polishing"}` — активна послуга.
- `{"kind":"package","id":"f0300000-0000-4000-8000-000000000001"}` — активний пакет.
- `{"kind":"individual"}` — індивідуальний підбір.

`carClassId` — ідентифікатор активного класу, наприклад `sedan`. Його можна додати до будь-якого варіанта запису. Назву послуги або пакета бере сервер із каталогу. Додаткові ключі, зокрема ціна або назва від клієнта, відхиляються. Консультація не приймає параметрів каталогу чи розкладу.

Телефон після нормалізації має формат `+380XXXXXXXXX`. Допустимі місцевий префікс `0` та міжнародні `+380`, `380`, `00380`, пробіли, дужки, крапки та дефіси. Телефон не підтверджує особу і не пов’язує заявку з карткою клієнта. Ім’я обмежено 120 символами, модель — 160, коментар або запитання — 2000. У багаторядковому тексті `CRLF` перетворюється на `LF`. Інші керівні символи C0/C1 відхиляються.

### Дата й час

Дата у форматі `YYYY-MM-DD` необов’язкова. Сервер приймає дати від поточної дати в `Europe/Kyiv` до неї плюс 90 календарних днів включно. Слот також необов’язковий. Без дати слот зберігається як побажання. Інтервал на сьогодні доступний до моменту завершення. Для `21:00-00:00` завершення настає опівночі наступного дня.

| Сценарій | Стабільні ідентифікатори слотів |
| --- | --- |
| Обидві форми | `10:00-12:00`, `12:00-15:00` |
| Сторінка запису | `15:00-18:00`, `18:00-21:00`, `21:00-00:00` |
| Модальна форма | `15:00-19:00`, `19:00-23:00`, `night_by_arrangement` |

Для `night_by_arrangement` дата перевіряється за тим самим 90-денним правилом. Слот доступний упродовж усієї вказаної дати і не має фіксованого часу завершення. Це заявка на узгодження візиту.

**Етап 7.5.** Синхронізувати клієнтську перевірку дати з горизонтом 90 днів у `Europe/Kyiv` замість поточної межі 2099 року. Передавати стабільні ідентифікатори каталогу й слотів. Майбутня Edge Function перетворюватиме UUID від RPC на `{ success: true, booking_id }`.

## Захист створення заявок

Єдина сигнатура запису — `public.create_booking_request(p_request jsonb, p_idempotency_key text)`. Формат `p_request` наведено вище. RPC повертає UUID для першого успіху та для повтору того самого нормалізованого запиту до закінчення строку ключа. Перший і повторний успіх можуть мати однакову HTTP-відповідь `200` з тілом `{ success: true, booking_id }`.

Ключ — 32 випадкові байти, представлені 64 малими шістнадцятковими символами. Клієнтська інтеграція має отримати байти криптографічним генератором для кожної нової спроби створити заявку та повторно використовувати той самий ключ для повторів цієї спроби. Майбутня Edge Function передаватиме заголовок `Idempotency-Key` параметром `p_idempotency_key`. Перевірка формату на сервері не визначає ентропію ключа.

| Обмеження | Початкове значення |
| --- | --- |
| Нові заявки на один нормалізований номер | 3 за ковзні 15 хвилин і 10 за ковзні 24 години |
| Нові заявки на весь маршрут | 30 за ковзні 60 секунд |
| Строк дії ключа | 24 години від першого успіху |

Ліміти спільні для `booking` і `consultation`. Повтор успіху не витрачає квоту. Зміна нормалізованих даних із чинним ключем повертає конфлікт. Після завершення строку ключа виклик знову проходить перевірки нової заявки. Номер телефону сам по собі не дає змоги отримати результат попередньої заявки.

Приймання заявки, перевірка лімітів та запис технічної події серіалізуються оновленням єдиного рядка `premiumwash_private.booking_protection_settings` в одній транзакції. Помилка відкочує заявку й технічну подію. Налаштування змінює власник БД. `service_role` має лише виклик єдиного RPC для запису, без доступу до таблиць захисту та прямої вставки.

Таблиця подій містить UUID заявки, часові позначки й окремі HMAC-SHA256 для ключа, нормалізованого телефону і нормалізованого запиту. Оригінальні значення в її полях відсутні. Секрет HMAC генерується в БД і зберігається окремо від подій у приватному рядку налаштувань. Заміна секрету змінює всі відбитки, тому не змінюйте його в активних вікнах без окремої процедури ротації.

| SQLSTATE | Код | Перетворення в майбутній Edge Function |
| --- | --- | --- |
| `PW014` | `INVALID_IDEMPOTENCY_KEY` | HTTP 400 |
| `PW015` | `IDEMPOTENCY_CONFLICT` | HTTP 409 |
| `PW016` | `RATE_LIMITED` | HTTP 429. `Retry-After` — додатне число секунд з `details`. Сервер бере час відкриття найпізнішого з перевищених вікон. |
| `PW017` | `PROTECTION_UNAVAILABLE` | HTTP 503. Запис блокується. |

Коди `PW001–PW013` зберігаються. У відповіді Edge використовуйте код і безпечне повідомлення. Значення `details` обробляйте лише як `Retry-After` для `PW016`. Не копіюйте сирі помилки БД, тіла заявок, ключі чи телефони в журнали.

### Очищення

Успішне створення видаляє партію до 256 технічних подій, для яких минули і строк ключа, і всі чинні вікна. Закінчення строків перевіряється незалежно від фізичного видалення. Під час простою власник БД може запускати такий самий обмежений прохід вручну. Він блокує той самий рядок налаштувань і не видаляє заявки.

```sql
BEGIN;
UPDATE premiumwash_private.booking_protection_settings
SET lock_token = NOT lock_token
WHERE singleton;

WITH policy AS (
    SELECT clock_timestamp() AS now_at, greatest(phone_long_seconds, endpoint_seconds) AS keep_seconds
    FROM premiumwash_private.booking_protection_settings WHERE singleton
), expired AS (
    SELECT event.booking_id
    FROM premiumwash_private.booking_protection_events AS event CROSS JOIN policy
    WHERE event.expires_at <= policy.now_at
      AND event.accepted_at <= policy.now_at - make_interval(secs => policy.keep_seconds)
    ORDER BY event.accepted_at, event.booking_id
    LIMIT 256
)
DELETE FROM premiumwash_private.booking_protection_events AS event
USING expired WHERE event.booking_id = expired.booking_id;
COMMIT;
```

Зміна строку ідемпотентності застосовується до нових подій. Якщо збільшити вікно ліміту, вже видалена історія не відновиться. Автоматичний фоновий запуск очищення не налаштований.

## Локальна Edge Function

`POST http://127.0.0.1:54321/functions/v1/submit-booking-request` приймає `booking` і `consultation`. Об’єкт заявки передається в тілі JSON, ключ із 64 малих шістнадцяткових символів — у заголовку `Idempotency-Key`. Повтор тієї самої дії використовує той самий ключ, зокрема після втрати відповіді або тайм-ауту запису. Успішна відповідь і успішний повтор мають статус `200` і тіло `{ success: true, booking_id }`.

- Функція приймає `application/json` з необов’язковим `charset=utf-8` і відхиляє стиснення. Ліміт **16 384 байти** перевіряється за оголошеною довжиною та під час читання потоку, зокрема без `Content-Length`.
- Читання має загальний тайм-аут **5 с**. Виклик допуску має тайм-аут **2 с**, виклик запису — **5 с**. Запит, який не отримав підтвердження допуску, не викликає запис.
- Відхиляються невалідні UTF-8 і JSON, дублікати ключів навіть із різними JSON-екрануваннями, невідомі поля та несумісні типи. Окремий сканер розпізнає лише рядкові токени й пунктуацію після перевірки граматики через `JSON.parse`. Каталог, телефон, довжину контактних полів і розклад перевіряє захищений RPC.
- Серверний ключ і URL надає локальний Edge Runtime. Заголовки клієнта не передаються до бекенду. У конфігурації лише `submit-booking-request` має `verify_jwt: false`. Функція не використовує IP-заголовки.

Помилки мають тіло `{ success: false, code, message }` зі статичним українським повідомленням. `PW001` і `PW014` повертають `400`, `PW002–PW012` — `422`, `PW013` — `500`, `PW015` — `409`, `PW016` — `429`, `PW017` — `503`. Для `PW016` передається лише перевірена затримка в секундах через `Retry-After`. Непідтверджена відповідь RPC має загальну помилку. Усі відповіді функції мають `Cache-Control: no-store`.

### Облік HTTP-спроб

Функція викликає `admit_booking_http_attempt()` до обробки методу, origin і тіла. Бюджет спільний між незалежними екземплярами й допускає **120 спроб за ковзні 60 секунд**. Спроби, що дійшли до функції, витрачають допуск навіть за невалідного тіла, відхиленого origin чи повтору. Допуск фіксується окремим запитом PostgREST до виклику `create_booking_request`, тому помилка заявки його не повертає.

Нуль від RPC допуску означає успіх. Додатне число — `HTTP_RATE_LIMITED`, статус `429` і `Retry-After`. Помилка допуску — `PW017` і `503`. Для запису бізнес-даних, як і раніше, використовується лише `create_booking_request(jsonb,text)`.

Рядок у приватній схемі містить до 120 часових позначок без ідентифікаторів клієнтів. Прострочені позначки ігноруються та прибираються під час наступного допуску. `service_role` може викликати технічний RPC. Прямого доступу до рядка ця роль не має. Власник функції `premiumwash_http_gate` не має входу до БД, обходу RLS або прав запису заявок.

### Функція, штатний Kong і внутрішній маршрут

| Рівень | Зафіксована поведінка |
| --- | --- |
| Обробник функції | Приймає origin `http://localhost:5173` або `http://127.0.0.1:5173`. Коректний preflight повертає `204` з точним origin, дозволом `POST` і заголовками `Content-Type, Idempotency-Key`. Для іншого origin функція повертає `403`. Запит без origin може пройти без заголовка CORS. |
| Штатний локальний Kong на `127.0.0.1:54321` | Перехоплює браузерний preflight і повертає `200` з `Access-Control-Allow-Origin: *` до виконання функції. Такі запити не витрачають бюджет функції. Фактичний `POST` доходить до обробника, який перевіряє origin і може повернути `403`. Kong може додати `*` і до цієї HTTP-відповіді. |
| Внутрішній тестовий маршрут | `http://supabase_edge_runtime_premiumwash-2-local:8081/submit-booking-request` доступний зі Studio у bridge-мережі. `OPTIONS` надходить до функції. Порт Edge Runtime не публікується на хості. |

```powershell
node --test supabase/tests/http/bookingHandler.test.mjs
supabase test db --network-id premiumwash-2-local-loopback
node supabase/tests/integration/bookingProtectionConcurrency.mjs
```

Останній сценарій порівнює маршрути, перевіряє бюджет, повтори, конфлікт, тайм-аут допуску й структуровані логи. Він видаляє лише створені ним синтетичні заявки та відповідні записи ідемпотентності. Запити до платформи Supabase та перевірки hosted-шлюзу до цього сценарію не входять.

### Локальний запуск сайту

У окремому вікні PowerShell запустіть сайт із кореня репозиторію. Змінні процесу мають пріоритет над `.env.local`, тож цей файл редагувати не потрібно.

```powershell
$env:VITE_BOOKING_MODE = 'live'
$env:VITE_TURNSTILE_SITE_KEY = '1x00000000000000000000AA'
$env:VITE_BOOKING_API_URL = 'http://127.0.0.1:54321'
$env:VITE_SUPABASE_URL = 'http://127.0.0.1:54321'
$env:VITE_SUPABASE_ANON_KEY = 'your-anon-public-key-here'
npm run dev -- --host 127.0.0.1 --port 5173 --strictPort
```

Відкрийте `http://127.0.0.1:5173`. Значення `VITE_BOOKING_API_URL` — базова адреса API без шляху. Клієнт надсилає заявки без облікових даних. Заглушка для публічного ключа вимикає читання каталогу через SDK, тому сайт показує вбудований каталог. Для читання з локальної БД у цьому ж процесі можна задати публічний ключ саме локального проєкту. Закрийте вікно PowerShell після роботи, щоб скинути змінні процесу.

З `VITE_BOOKING_MODE=demo` форми лише імітують надсилання. У `live` відсутність адреси API, помилка мережі або відмова сервера показують помилку. Перемикання на інший сервер чи на деморежим після помилки немає.

Для локальної перевірки Turnstile використовуйте лише офіційний тестовий site key `1x00000000000000000000AA` і серверний secret у змінній Edge Function `TURNSTILE_SECRET_KEY`. Тестовий secret не можна додавати до production.

Ключ і дані для повтору зберігаються в пам’яті відкритої форми. Після втрати підтвердження повторіть надсилання з тими самими даними в тій самій формі. Після перезавантаження сторінки або закриття вікна консультації цей ключ відновити неможливо. Клієнт припиняє повторення непідтвердженої заявки через 24 години й пропонує уточнити її стан. Відповідь `429` із коректним `Retry-After` тимчасово блокує надсилання. Автоматичних повторів немає.


У прикладі перевірки збірки використовуються тестові значення змінних. Перевірка шукає їх у зібраних файлах, а також перевіряє відсутність старих RPC і розпізнаваних серверних облікових даних.

### Перед публікацією

- Підтвердити hosted origins, поведінку preflight і межу обліку на шлюзі. Локальні тести не підтверджують hosted CORS чи довірений IP.
- Інтегрувати Cloudflare Turnstile після окремого погодження, із серверною перевіркою токена та правилами безпечного повтору. CAPTCHA знижує автоматизоване навантаження. Для захисту від вичерпання ліміту за чужим номером потрібне окреме рішення. Спільний бюджет може бути вичерпано навмисно.
- Перевірити політику журналів шлюзу й платформи до публікації. Власні логи функції містять лише випадковий ID запиту, етап, статус, код і тривалість.
